## 0. 先看这一页：现在怎么推进

### 0.1 三条执行原则

1. **按报告框架组织成果，按技术依赖安排工作。** 背景写作与候选核验可以并行；不必写完前两章才开始实例化，也不能在实验前写好“哪个方案最好”的结论。
2. **已有定理引用为主，适配论证与改动补证为重点。** 不要求每个候选从零重证原论文；但原文定理的前提、已发现的证明疑点、具体参数和实现差异必须有处置结论。
3. **先形成合格基线，再扩大比较范围。** 原型跑通不等于安全实例通过；新增候选不能挤掉完整系统、错误输入拒绝、不同实例比较及优化验证等赛题工作。

### 0.2 任务依赖

T01 背景与问题界定，可与后续任务并行推进。

T02 场景与评价标准 → T03 通用构造要求 → T04 候选筛选 → T05 适配论证与参数核验 → T06 完整实例与功能检查 → T07 基线评测 → T08 优化及复核 → T09 场景化比较 → T10 报告与交付。

T08 一旦改变算法、参数或随机性，必须回到 T05／T06 复核，并重跑受影响的 T07。T03—T07 可对不同候选分批推进，无须等所有候选同时准备好。

### 0.3 紧接着先做什么

- [ ] 建立 T02 的“场景—约束—指标”表，先明确比较目标。
- [ ] 从通用构造原文提取 T03 的组件要求表，不凭“都是格算法”判断可以组合。
- [ ] 整理 T04 的候选状态：已核验、待核验、仅文献参考、暂不适配；旧排序不是新准入结论。
- [ ] 将既有 Foo–Li／MP12 成果挂到 T05，只补实际选用路线必须解决的缺口。
- [ ] 与队长确认首批组合、参数安全目标、查询／失败预算和实验资源。最终算法与参数仍由队长冻结，你提供约束与评估依据。

**当前最优先交付物是上述三张表与一份首批评估清单，不是继续无限扩展 Lean 形式化。**

## 1. 要求分层：什么必须做，什么是我们的质量目标

| 标记 | 含义 | 本计划中的处理 |
|---|---|---|
| O：官方要求 | 来自用户提供的赛题原件；A01—A15 是内部映射编号 | 不得通过简化报告目录而省略 |
| Q：团队质量目标 | 老师要求的横向比较、用户提出的场景化选型、证据可复核 | 明确写入任务，但不伪称官方评分门槛 |
| M：内部检查方法 | 参数账本、测试矩阵、复核记录、版本指纹等 | 可以调整方法，不能降低所支撑要求 |
| X：可选扩展 | 新环／模结构迁移、新构造、进一步机器形式化等 | 先评估必要性、风险和工作量，不自动列为主线前置条件 |

官方明确要求至少一种完整 LWE／SIS 实例，同时要求可切换组件以及不同参数、不同格方案实例的尺寸、时间、内存比较。因此，只有一个演示实例跑通不能据此认定全题达标。

官方未规定必须 Ring-SIS、128 位安全、某个固定速度、测试次数或优化百分比。若团队选择这些目标，必须标为 Q，并记录理由。

赛题“内容”包含底层算法及 IBS 优化；**基础优化与收益验证不是全部可选**。可选的是进一步提出新的融合构造、环迁移等高风险研究扩展。

遵照老师本次意见，准确描述选定方案原有的安全模型和强度，不把提升到 QROM 设为统一任务。经典模型中的证明与量子攻击成本估计分栏记录；不能据此自动声称整个系统已经获得量子对手模型下的正式证明。

## 4. 逐项任务与达标要求

### T01｜研究背景与问题界定

**做什么**

- 说明 IB-ME 的来源、功能目标、参与方和信任假设；区分身份匹配、发送者认证、隐私与在线交互式身份认证。
- 说明为什么关注抗量子实例；相关发展事实在正式写作时查证标准机构／原论文等一手来源。
- 对相关工作按功能、假设、模型和工程能力分类，不写成互不关联的论文摘要堆砌。

**交付物**：背景草稿、术语表、文献来源表。

**达标条件**

- [ ] 能用一段话说明“研究问题—现有选择困难—我们的比较方法—预期交付”。
- [ ] 文献事实能定位到原始来源；尚未核实的性能或安全主张标为待核验。
- [ ] 不把 IB-ME 这一功能概念本身等同于抗量子安全，也不把研究目标写成已实现贡献。

**不要求**：在实例研究前写完最终引言；不要求穷尽全部文献。

### T02｜场景与评价标准

**做什么**：先确定代表性需求，再确定指标和工作负载。场景标签不等于已经完成实际行业部署。

| 建议场景 | 待冻结的工作负载／约束 | 主指标 | 必须同时观察的代价 |
|---|---|---|---|
| 带宽／存储敏感 | 消息长度、发送次数、公共参数分发频率 | 密文长度、累计通信／存储量 | 密钥和公共参数成本、加解密时间 |
| 接收端资源受限 | 可用内存、接收频率、可接受延迟 | 解密时间、接收者密钥尺寸、峰值内存 | 系统建立／发钥成本及发送端负担 |
| 高频通信 | 每密钥消息数、用户数、身份复用比例 | 在线延迟、吞吐量 | 预计算成本、缓存占用、密钥生命周期 |
| 发钥服务压力大 | 新用户数、发钥／派生频率 | 发钥／派生时间与存储成本 | 公钥尺寸、初始化成本、用户端成本 |

**交付物**：场景卡。每张包括“为什么需要 IB-ME、威胁与信任条件、负载、硬约束、主次指标、测试环境”。

**达标条件**

- [ ] 正式测量前冻结首批场景和比较指标；数值约束要来自应用依据或明确标为团队模拟设置。
- [ ] 不在得到结果后偷偷改变场景权重；需要调整时保留旧设置和理由。
- [ ] 软件模拟资源受限场景不等于真实嵌入式硬件验证；不引入硬件制作任务。

**建议范围 Q**：首批选 3 类代表场景，第四类视实际瓶颈增补。数量不是官方门槛。

### T03｜通用构造要求与接口表

**做什么**

- 固定老师论文及通用构造的具体版本、构造编号和定理编号。
- 提取 HIBE 的层级、匿名性、攻击模型、身份查询限制，以及 IBS 的身份／签名查询能力和不可伪造目标。
- 列出 Setup、发送者／接收者发钥、加密、派生、解密和验证的输入输出、随机性、失败语义与调用关系。
- 核对签名究竟绑定哪些身份与消息字段，HIBE 实际承载什么，载荷编码是否有歧义。

**交付物**：一张构造流程图或调用表、一张“构造前提—组件定理—实现接口”表。

**达标条件**

- [ ] 每项组件要求有原文出处，不以名称相似代替定义匹配。
- [ ] 正确性、隐私、认证、篡改拒绝分别列出，不用一个“安全”标签统包。
- [ ] 两层身份顺序、消息空间、签名序列化和失败返回全部对应。
- [ ] 明确通用构造已经覆盖的性质与需要额外处理的性质，尤其是外层密文完整性。

### T04｜候选筛选与首批组合

**做什么**

- 将旧候选文档作为入口，逐项补充当前核验状态，不直接继承旧“排名第一”的结论。
- 用具体方案和版本命名候选；LWE、SIS、Ring-SIS 是假设类别，不能代替完整方案。
- 优先采用已有证明、参数可核对、实现可获取或可完成的组件。
- 对不同困难假设保留拓展入口，但不因题目名称而强行制造未经证明的环／模迁移。

**交付物**：候选表与短名单。字段至少包括方案／版本、困难假设、安全定义与模型、定理位置、正确性／参数条件、实现来源、适配缺口、成本依据、状态、保留或淘汰理由。

**达标条件**

- [ ] 入选“正式系统比较”的候选已通过 T03 所需性质核对；尚有实质缺口的只能列为研究候选。
- [ ] 不适配匿名性或身份模型的方案，可保留为异功能参考，但不得与合格实例混成同一胜负排名。
- [ ] 给出可复核的入选理由；不能只依据论文年份、渐近复杂度或其他机器上的单项速度。
- [ ] 队长确认首批路线和后备路线；未确认前不宣称最终选型完成。

**建议范围 Q**：首批力争 2 个合格完整组合，条件允许再增加。优先固定一个 HIBE 比较不同 IBS，或固定一个 IBS 比较不同 HIBE，避免一开始全面交叉组合。不能用 mock 或同一方案改名字冒充不同格方案实例。

### T05｜组合适配、正确性、安全性与参数核验

**做什么**

1. **引用原证明**：记录定理的假设、模型、结论、参数条件和归约损失。
2. **论证可组合**：逐项说明所选 HIBE／IBS 为什么满足通用构造要求；若只需应用现成定理，写清代入过程，不重抄全篇证明。
3. **补必要缺口**：论文审查中已指出的问题、缺失引理、构造改动和实现偏离分别处置。
4. **做具体参数核验**：把正确性、采样、困难性、查询规模与资源约束放进同一张账本，不能分别选出互不兼容的参数。
5. **校准安全声明**：正式归约界、已知攻击成本估计和实现测试分栏记录。

**交付物**

- 每个组合一份适配说明与安全声明卡。
- 每个参数集一份可重算账本：维数／模数、噪声／宽度约定、范数条件、失败与统计误差预算、公开分布条件、查询上限、估计器版本／命令及资源估算。
- 一份差异表：论文算法、实际采样器、随机源、种子持久化、编码、重试／中止、载荷适配与安全包装。

**达标条件**

- [ ] 所声明性质的证明链能逐项追溯；实质性未决问题没有被“论文已证明”四字掩盖。
- [ ] 合法输入的恢复／验签条件，以及初始化、委派、采样、解密等失败事件有适用范围明确的界。
- [ ] 不把重复重放视为独立试验，也不把预定批次结论自动扩展到任意自适应查询。
- [ ] 参数同时满足声明所需条件；未知常数、未指定预算或未证的近似误差不填成零。
- [ ] 安全估计注明攻击模型和工具设置；不把底层攻击成本估计直接等同于整个 IB-ME 的严格安全下界。
- [ ] MP12 等工具的原定理适用条件、有限采样误差与程序行为有核验依据；代码名称相同不算证据。
- [ ] 参数与安全声明经队长确认，关键证明适用性问题提交老师／独立审阅者复核；未解决项保留“条件通过”或“暂缓”。

**边界**

- 不要求从零重证所有组件，不要求所有候选全部 Lean 化。
- 不要求证明真实 SHAKE 是真随机；如依赖 ROM，准确说明模型与实际实例化假设。
- 不额外开展 QROM 强化，但也不把经典 ROM 证明改称为完整量子安全证明。
- 只有满足此项相应门槛的配置，才进入“同等安全目标”的正式性能比较。调试配置可先用于测通流程，但必须单列。

### T06｜完整系统实现、正确性与拒绝行为

**做什么**

- 将选定组件接入正式接口，贯通系统建立、发钥、身份匹配、加密、解密和验证。
- 检查消息加签名的真实载荷；不能只测原论文的一比特加密就声称完成任意字节消息。
- 单独检查外层密文完整性；需要新增包装时，先明确威胁模型和证明义务。
- 保留旧公开伪造与篡改脚本作为负面对照，在新版本上回归。

**交付物**：可运行入口、配置、测试用例、完整尝试记录、失败分类与回归报告。

**达标条件**

- [ ] 合法匹配的预先规定测试批次全部正确恢复原始消息；不得删去失败样本后报“全通过”。
- [ ] 覆盖仅发送者错误、仅接收者错误、双方错误、非法／边界身份、空消息及载荷边界。
- [ ] 覆盖签名、密文、身份绑定、截断、追加、重复字段、非法模数表示及伪造输入。
- [ ] 对错误身份和规定的篡改／伪造用例按规范拒绝；自我伪造测试明确攻击者持有什么密钥。
- [ ] 中止、超时、质量拒绝、重试、损坏状态分别计数；重试规则不改变证明中假定的分布而未说明。
- [ ] 不同实例确实经统一接口切换；mock 不计为安全格实例。
- [ ] 旧反例的修复有新版本证据。攻击失败只是回归证据，不写成普遍安全证明。

**停止条件**：一旦出现有效伪造、应拒绝的篡改被接受或正式批次合法解密失败，暂停该配置的“达标”认定，保留样本并定位原因；修复后建立新的完整批次。

### T07｜统一性能评测

**做什么**：分开测组件成本与完整 IB-ME 成本；同时展示方案维度和参数维度。

**交付物**：评测协议、原始 CSV／JSON、环境与版本记录、尺寸账目、统计表和绘图入口。

**必须覆盖的指标**

| 类别 | 必测对象／口径 |
|---|---|
| 尺寸 | 系统公共参数／公钥、主密钥、发送者密钥、接收者密钥、签名、完整密文；逐项明确是否含种子、缓存、认证包装和序列化头 |
| 时间 | Setup、发送者／接收者发钥、需要的派生、签验、完整加密／解密；区分冷启动、预计算与在线阶段 |
| 内存 | 明确进程峰值 RSS 或其他选定口径；说明是否包含解释器／原生库、预计算和缓存，不把 Python 对象大小当作完整进程内存 |
| 稳定性 | 成功、失败、中止、重试与超时数量；不能仅保留成功运行的耗时 |
| 环境 | CPU、内存、系统、语言／编译器、库版本、线程、优化选项、实际加速路径；未用／未测的加速明确标注 |

**达标条件**

- [ ] 每行结果都能定位到方案、参数、代码版本、场景、运行编号和测量命令。
- [ ] 理论编码尺寸与实际序列化尺寸分开；消息长度一致时才直接比较完整密文。
- [ ] 正式同组比较保持安全目标、功能／隐私要求和失败预算可比；不能只令两个方案的 n 相同。
- [ ] 同一环境中的测量与论文作者结果分表；不同语言或优化成熟度产生的影响如实说明。
- [ ] 同时保留中位数与离散程度；若报告均值、尾延迟或置信区间，要给出相应样本量和统计方法。
- [ ] 若因成本只能得到少量样本，标为探索结果，不据此声称稳定领先或“显著提升”。
- [ ] 在单独的时间／内存测量中控制分析工具的额外开销；他人可从原始数据重新得到图表。

### T08｜优化及保持性复核

**做什么**

- 根据基线测量选择瓶颈，明确优化的是重复计算、序列化、代数实现、签名结构还是其他部分。
- 将“实现等价优化”和“改变构造／分布的优化”分别处理。
- 先保存基线；每轮优化只引入可识别的改动，测量获益与代价。

**交付物**：优化前后差异说明、保持性论证、参数重检、回归结果和相同条件下的成本对比。

**达标条件**

- [ ] 实现优化说明输出语义和所需随机性保持；不能靠复用不允许复用的秘密随机数换速度。
- [ ] 结构性优化补充受影响的正确性和安全论证，并重新检查通用构造适配性。
- [ ] 两个版本在相同功能、安全目标、消息／工作负载下比较；若参数必须改变，单列原因和影响。
- [ ] 报告每项收益、内存／预计算代价、未改善项及失败情况，不只挑有利指标。
- [ ] 新配置重新通过 T05／T06，并重测受影响的 T07 项目。
- [ ] 不把环移植、复杂度降低或“融合方案”仅凭设想写成已完成创新。

**达标口径**：不能只写“做了优化”。应有可复核的成本下降证据，并明确作用范围；若某次尝试没有收益，如实保留为负面结果，不能用它冒充已达到优化效果。

### T09｜横向比较与场景化结论

**做什么**

- 按 T02 的既定需求解释尺寸、速度、内存及一次性成本之间的取舍。
- 分开比较“同一安全目标下不同方案”和“同一方案不同参数”。
- 对高频通信说明成本摊销条件，对资源受限场景说明是否真实满足约束。

**交付物**：综合表、场景推荐表、结论到原始结果的索引。

**达标条件**

- [ ] 每个“更快／更小／更适合”的结论都带比较对象、参数、负载、环境和证据。
- [ ] 指标差异不足以支持排序时写“未观察到稳定优势”或“证据不足”，不强行分胜负。
- [ ] 安全性质或实现完整度不同的候选不能靠综合评分掩盖差异。
- [ ] 说明适合什么、不适合什么、代价是什么；不声称存在脱离条件的全局最佳算法。
- [ ] 没有实际行业部署证据时，用“所设工作负载下的适配建议”，不写成生产部署结论。

建议结论句式：

> 在【安全声明及模型】【参数】【消息长度／用户规模】【实验环境】下，组合 A 相比组合 B 的【指标】变化为【实测值】；代价是【另一指标／条件】。因此，在本文设置的【场景约束】下优先考虑 A；该判断不外推到【未测范围】。

### T10｜报告、复核与最终交付

**做什么**

- 由 T01—T09 的证据填充报告，而不是重新写一套与代码脱节的故事。

**交付物**：完整报告、源代码与依赖说明、配置、原始结果、图表生成入口、演示说明、A01—A15 验收表。

**达标条件**

- [ ] 摘要与结论中的每个成果主张都有正文及证据支撑。
- [ ] 报告图表能由归档数据重建，演示与报告使用相同或清楚对应的版本。
- [ ] 每个 A01—A15 条目写明状态、证据、范围与缺口；仅有计划或文档自述不判为通过。
- [ ] 不上传生产私钥、持久秘密种子或敏感快照；可复现测试种子与真实秘密分开。

## 5. 首批实验范围与资源约束（团队建议，待确认）

### 5.1 待检验的问题，不预设赢家

| 问题 | 实验／核验方式 | 允许出现的结论 |
|---|---|---|
| 更短签名是否显著减少完整 IB-ME 密文？ | 固定 HIBE、消息与安全目标，对比 IBS／签名长度和最终密文 | 收益明显、被 HIBE 开销抵消、或当前证据不足 |

| 优化是否只把在线成本转移到预计算？ | 分开测预处理、在线阶段、缓存及累计成本 | 总成本下降、仅高复用时获益、或没有收益 |
| 不同参数是否改变场景选型？ | 在各自合格参数档下重复同一评测协议 | 排名稳定、发生反转、或无法比较 |

### 5.2 冻结实验表中的变量

- 自变量：候选组合、参数档、消息长度、用户／消息数量、优化开关。
- 因变量：尺寸、时间、内存、中止／失败等。
- 控制项：安全／功能目标、失败预算、工作负载、硬件、软件栈、线程、计时边界及统计方法。
- 同一目标下不同方案的具体参数可以不同；不能为了“控制变量”强迫它们使用不合理参数。
- 测试种子及其用途可归档；同一固定种子的重放只验证复现，不充当独立统计样本。

**首批建议 Q**

1. 先做两个合格组合的有限比较，再决定是否增加第三个；先单组件替换，后考虑交叉组合。
2. 展示不同参数档；档位的安全目标和适用范围先经 T05 确认。不得把正式参数与故意弱化的调试参数混作同安全比较。
3. 功能测试包括空消息、最短有效身份、最大允许长度及越界输入；性能测试选择共同支持的短／中／长载荷，具体字节数先冻结。
4. 将冷启动与热缓存、同一身份重复通信与新身份通信分开；避免隐含缓存决定胜负。
5. 重复次数先由小规模试跑估算成本后冻结；试跑结果不用于挑选有利种子或删去慢样本。
