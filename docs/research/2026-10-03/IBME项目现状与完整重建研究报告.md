## 1 主要结论与建议

我们目前做的是一个以两层格基 HIBE 和格基 IBS 为底层组件的身份基匹配加密原型。它已经把系统建立、发送者密钥提取、接收者密钥提取、加密、双向身份检查和解密串起来，拥有较清晰的模块接口、编码规则、命令行和测试。这些是可以保留的工程资产。

但当前原型还不能作为安全完整的竞赛成品。我们在初次核验中执行了公开参数伪造攻击：攻击者不需要 Alice 的发送者密钥，就能产生接收者认可为 Alice 所发的密文。另一项初次实验只修改密文一个字节，解密接口仍返回原消息，说明其密文完整性与赛题的篡改拒绝要求存在明确差距。全套测试的 333 项通过、10 项跳过，并没有排除这些问题。

建议采用“保留工程组织，重新建立密码学依据”的重建方式：先冻结安全目标、论文版本和算法，再建立证明条件、参数和实现之间的对应关系。不能只把矩阵维度调大，或给现有方案换上短签名，就宣称完成了安全升级。现有 HIBE 与 ABB10 原论文的具体算法结构不同，陷门采样也有教学性简化；这些差异必须逐项处理。

**下一阶段必须系统调研 HIBE 和 IBS。** 王老师论文 §4 的通用组合已经选定，底层要求仍需逐项核验：HIBE 的两层委派、自适应匿名安全性，IBS 的自适应不可伪造性，以及实际密钥复用、采样分布和参数条件。其它 IBME 文献保留为安全定义与相关工作参照，不再承担重新选择通用构造的任务。[S1]

建议把项目分成三层成果：第一层是论文算法一致、参数有依据的 LWE/SIS 完整参考实例；第二层是在同一通用构造下形成至少另一套可运行的 HIBE 或 IBS 组合，优先研究已有完整 Ring-SIS IBS，并核验环格和模格 HIBE 的适配可能；第三层是有安全论证和消融实验支持的优化、可复现评测和应用演示。第二层的额外实例数量与研究深度是内部目标，不能写成赛题强制要求。

国赛一等奖不能由某个方案名称或代码量保证。最有说服力的成果是：我们准确识别了哪些性质来自论文，哪些优化由自己完成；能够解释并复现攻击、修复、参数选择和性能收益；对没有实现或没有证明的性质，说明其边界。

## 3 赛题要求及其正确解释

赛题的重点有三项：通用构造与可组合实例化；抵御自我伪造和篡改的认证能力；通过底层算法及 IBS 优化降低尺寸和计算开销。软件应能展示参数、密钥生成、加密解密、身份匹配、签名验证、实例切换和性能测试。

| 原文指标 | 我们需要提供的证据 | 容易误判的地方 |
|---|---|---|
| R1 完整流程及双向匹配 | 五个算法的流程、正确性说明和四种匹配情况 | 返回失败不等于恶意用户无法绕过本地检查 |
| R2 可切换组件及 LWE/SIS 完整实例 | 实际配置、兼容性检查、端到端运行、论文与参数依据 | mock 或预留接口不等于另一套格方案已实现 |
| R3 隐私 认证 完整性 | 对应安全定义、组合前提、参数与攻击核验 | 签名验证通过的消息认证不自动覆盖所有密文字节 |
| R4 批量正确性及错误输入拒绝 | 身份和消息生成方法、样本数、失败日志、攻击测试 | 只测试随机伪造会漏掉线性代数等定向攻击 |
| R5 参数和实例的性能对比 | 各类密钥与密文尺寸、时间、内存、原始数据与图表 | 一种方案换几个小参数，不足以展示不同方案实例 |

赛题最低明确要求至少一种 LWE/SIS 完整实例，并能扩展其他格困难假设组件。它没有明确要求全部环格和模格变体必须完成，也没有给出固定测试次数、速度上限、128 位安全门槛、指定开发语言或公开评分权重。我们可以自设更高目标，但报告必须把官方要求与团队目标分开。

C/C++ 出现在所需知识中，可作为优化实现路线；它不意味着 Python 参考实现不允许存在。建议保留易审查的 Python 或 Sage 数学参考层，把有实测瓶颈的运算迁移到 C/C++。64 位多核和 16 GB 以上内存是题目建议配置。

“抗量子”需要说明所采用的格困难假设与攻击模型。使用 SHAKE 或格矩阵并不能直接得到完整 QROM 证明，更不能得到 NIST 安全等级。标准模型与标准假设也不是同一个概念：一种方案可以基于标准 LWE 假设，但证明仍在 ROM 或 QROM 中。

题目没有明确指定 Boyen–Li 增强隐私。团队已决定不做这一性质，仍必须完成普通隐私、发送者认证、四种接口匹配情况和赛题要求的篡改拒绝。不能把取消增强隐私解释为取消匿名 HIBE，或允许忽略恶意接收者自我伪造。

## 4 我们现在做的是什么

### 4.1 用户与密钥的含义

IBME 可以理解为双方各自声明希望通信的对象。发送者 Alice 持有绑定自身身份的发送密钥，并将消息加密给指定接收者 Bob；Bob 持有绑定自身身份的接收密钥，并指定自己愿意接收的发送者 Alice。设实际发送者身份为 $\phi$，接收密钥身份为 $\rho$，加密指定的接收者为 $\mathrm{rcv}$，解密指定的发送者为 $\mathrm{snd}$，正确恢复要求

$$\rho=\mathrm{rcv}\quad\land\quad\mathrm{snd}=\phi.$$

系统中心生成主公钥和主密钥，并发放两种用户密钥。发送密钥用于身份证明，接收密钥用于取得消息。这里的“公开身份字符串”并不表示用户密钥公开，也不表示签名可以靠普通公钥签名直接替代。系统中心通常有生成用户密钥的能力，存在密钥托管信任；现实中的身份核验、发钥权限和撤销需要另外设计。

### 4.2 当前通用组合的五个算法

当前 `BaselineIBME` 实现采用两层 HIBE 加 IBS。HIBE 身份顺序固定为接收者在第一层、发送者在第二层，即 `(rcv, phi)`。这与“发送者先加密、接收者后解密”的时间顺序不同，不能交换。

Setup 分别建立 HIBE 和 IBS，输出组合公钥与组合主密钥。SKGen 为发送者身份提取 IBS 签名密钥。RKGen 为接收者身份提取 HIBE 第一层密钥。Enc 先对接收者身份和消息的规范编码签名，再把签名和消息放入 HIBE 加密载荷。Dec 用接收者密钥和期望发送者身份派生第二层密钥，解密、解析，再验签。

$$t\leftarrow\operatorname{IBS.Sign}(ek_\phi,\operatorname{Encode}(\mathrm{rcv},m)).$$

$$ct\leftarrow\operatorname{HIBE.Enc}(hpk,(\mathrm{rcv},\phi),\operatorname{Encode}(t,m)).$$

$$sk_{\rho,\mathrm{snd}}\leftarrow\operatorname{HIBE.Derive}(dk_\rho,\mathrm{snd}).$$

$$\operatorname{IBS.Verify}(ipk,\mathrm{snd},\operatorname{Encode}(\rho,m),t)=1.$$

最后一式成立且解析合法，接口才返回消息，否则返回 `BOTTOM`。密码输入失败与程序调用错误应区分：类型或配置错误可以抛异常，攻击者提供的非法密文应有稳定的拒绝语义。

将签名藏在加密内部有明确用途：公开可验的签名可能帮助攻击者枚举发送者身份。将接收者身份包含在签名消息内，则绑定消息的接收目标。但这些结构性安排只有在原语、参数和安全模型均满足组合定理时，才能支撑相应安全结论。Wang 等的通用构造是当前路线的重要理论依据。[S1]

### 4.4 底层算法目前的具体形式

当前陷门公矩阵采用 MP12 风格的 gadget 关系

$$A=[\bar A\mid G-\bar A R],\qquad A\begin{bmatrix}R\\I\end{bmatrix}=G.$$

这条代数等式能帮助构造短原像，但完整的论文采样还要求扰动、协方差条件、输出分布及陷门独立性。当前实现保留了代数骨架，没有实现完整证明所需的采样程序。它是“能求解方程”的实现，不足以认定为“满足论文要求分布”的实现。[S2]

当前 HIBE 的身份矩阵拼接为

$$B_{\mathrm{rcv},\phi}=[A\mid H(\mathrm{rcv})\mid H(\mathrm{rcv},\phi)].$$

对封装后明文的每个比特 $\mu_j$，代码重新采样均匀的模向量秘密 $s_j\in\mathbb Z_q^n$ 与高斯噪声，计算向量部分和标量部分

$$c_2^{(j)}=B_{\mathrm{rcv},\phi}^{T}s_j+e_2^{(j)}\pmod q.$$

$$c_{1,j}=u^{T}s_j+e_{1,j}+\mu_j\left\lfloor q/2\right\rfloor\pmod q.$$

解密使用派生陷门临时采样满足 $B_{\rho,\mathrm{snd}}x=u$ 的原像，计算 $c_{1,j}-x^{T}c_2^{(j)}$，按距离 0 或 $q/2$ 恢复比特，再解析并核对明文中加密保存的身份。这解释了当前密文体积和解密对小幅系数修改的容忍性。这里的随机秘密虽然在公开加密算法中生成，其实际取值不能公开或跨消息复用。

当前 IBS 使用身份矩阵 $F_{id}=[A\mid H_1(id)]$，签名为整数向量 $z$，验签检查非零、范数上界和

$$F_{id}z=H_2(id,m)\pmod q.$$

其用户密钥包含满足 $A\widehat R_{id}+G=H_1(id)$ 的矩阵。当前签名代码先采样 $x$，对 $H_2(id,m)-Ax$ 做确定性 gadget 比特分解得到 $y$，然后输出 $z=(x-\widehat R_{id}y,y)$，并重试直到满足范数界。由上述等式可直接验证签名方程，但该求解方式仍需与论文完整余类采样及输出分布对应，不能由代数自检替代这一审查。

方程与验签成功只说明代数约束满足，不说明找出合法短向量是困难的。原语级攻击正是利用了这一点。

### 5.2 初次核验的测试与攻击复现

2026 年 10 月 3 日对上述代码基点运行 `python -m pytest -q`，结果是 **333 passed, 10 skipped in 537.92s**。这证明既有测试在本机运行成功。它不证明 LWE 或 SIS 困难性，不证明匿名性，也不证明全体篡改输入都会被拒绝。测试时另有自查实验并行运行，因此该次测试时长不作为干净环境下的性能基准。

运行 `python experiments/attacks/forge_ibs.py`，原语级结果为：未提取 Alice 密钥的情况下，伪造签名范数约 185.81，验签界约 789.04，`verify` 返回真。协议级使用公开加密算法封装伪造签名后，接收方恢复了“AUTHORIZED BY ALICE: release the funds”，并将其归因于 Alice。脚本有两种层次，各运行一次；这是针对本仓库教学实现的攻击，不是对论文有效参数构造的破解。

第二项实验采用发送者 `Alice`、接收者 `Bob`、消息 `A`，分别为 5、3、1 字节。使用教学参数和固定测试种子 `review-2026-10-03`，对同一密文最后一个 `c1` 系数加一，从 7276 改为 7277。密文为 4,109,477 字节，其中仅一个字节不同。原始密文和修改后的密文均恢复 `A`；二者使用相同解码随机流，排除了随机派生差异的影响。这是一个明确反例，样本数为一，不能推断所有篡改都会成功。

## 6 当前关键缺口与重建理由

### 6.1 IBS 的公开线性代数攻击

当前 $F_{id}$ 是模 257 的 8 行、152 列矩阵。若能找到 8 个线性无关列，可仅在这 8 个位置解方程，其余位置置零，再把系数中心化到 $[-128,128]$。所得解满足

$$\|z\|_2\le128\sqrt 8\approx362.04<64\sqrt{152}\approx789.04.$$

因此验签方程与范数检查都可以通过，攻击者不需要陷门。旧说明只讨论了 152 个非零分量的稠密向量，漏掉了稀疏解。这个推导有“选取列满秩”的条件，本次攻击脚本实际找到了这样的列。

不能以“只缩小验签界”作为完整修复：需要同时保证合法签名分布、正确性概率、采样要求及 SIS 归约参数。验签界 $B_{sig}$ 与归约中得到的 SIS 解范数界 $\beta_{SIS}$ 也可能不同，应从定理推导，不能直接替换。

### 6.2 认证定理前提与基本 IBS 不一致

当前主要实现的是 Wang 方案中的基本短向量 IBS。论文及本地博士论文把基本形式证明到非自适应选择消息安全，即 UF-naCMA；通用 IBME 组合所需的 IBS 安全前提更强。相应自适应转换尚未在当前代码中完整落实。

此外，2026 年 Yu 等研究专门讨论同一身份重复查询时发送密钥的一致性。部署中会重复使用一把发送密钥，不能只验证每次重新发钥的模型。应逐篇核对 KeyGen、Sign 查询、主密钥秘密种子或缓存状态及安全游戏。这个新问题值得调查，但不能未经证明就宣布所有旧构造无效。[S3]

### 6.3 HIBE 名称与原论文算法不能等同

ABB10 CRYPTO 2010 的 §4 使用固定维度的身份相关矩阵变换和 BasisDel，典型形式为 $F_{id}=AR_{id}^{-1}$；当前实现则不断拼接身份矩阵块。它们的代数结构、委派算法、维度和采样需求不同。文件和类名中含有 ABB10，不能据此继承该论文的匿名性与安全证明。[S4]

在选择 ABB10 时还必须标明具体版本、章节和定理：§4 的 Theorem 5 是 ROM 中的自适应 INDr-ID-CPA；论文另有标准模型构造，不能把其不同章节性质拼到同一个后端上。两层情况下，证明中的查询相关损失也应进入具体安全评估。未来可以实现论文原算法，或给现有简化算法重新命名并仅保留为教学对照。

### 6.4 采样分布与哈希映射尚需完整处理

当前标量采样使用截断离散高斯拒绝采样，并非用均匀随机数冒充高斯。但标量统计测试不能验证整个陷门余类采样输出分布与论文一致。缺失的扰动步骤、平滑参数条件、谱范数约束、截断误差和浮点计算误差都应进入审查。

哈希到模空间的简单取模可能有偏差；需要按目标论文定义采用正确分布或量化偏差。身份哈希、消息哈希、密钥与协议上下文绑定也要统一。域分隔已存在，但任意追加新的输入字段都会改变方案定义，仍需说明其与证明中的随机预言机对应关系。

### 6.5 消息认证与密文完整性存在距离

Regev 风格加密有噪声容忍区间，修改某个系数后可能仍得到相同的消息和签名。隐藏在里面的签名依旧有效，接口就会接受修改后的密文。现有测试中有一项明确允许结果为 `BOTTOM` 或原消息，因此其通过不能证明满足赛题 R3 和 R4 的篡改拒绝要求。

Wang 的 Definition 10 排除已由加密查询得到的接收者、发送者、消息三元组。若密文字节改变而解出的消息与签名未变，它不构成该游戏中的新消息伪造；因此单字节反例不能直接被写成对论文加强认证定理的破解。它仍是赛题完整性验收的明确缺口，需要独立认证机制。[S1]

重建时要确定针对外部攻击者、持有接收密钥的攻击者、重放及合法重新加密，各自希望保证什么。合理的密码目标通常是拒绝未经授权生成或修改的密文，而不是无状态地把所有有效重加密都识别为“曾被改动”。随机数、重复密文记录和重放策略有独立语义。我们必须将赛题的拒绝要求落实为明确的输入类型与测试预期，并选用满足目标的认证组合。

在外层消息上加 AEAD 可以保护消息体，但若格密文胶囊或头部没有正确绑定，仍可能出现外层认证通过而胶囊被改动。CCA 安全和完整性不自动来自“加了 AES-GCM”这一步。这里研究的是固定通用构造的认证封装，不引入 Boyen–Li 提取器路线。

### 6.6 尚未形成多个完整实例与安全配置

当前没有可宣称安全的正式参数集。一般批量测试、多个格方案实例比较、原生内存统计及完整可视化仍需完成。现阶段能证明的是教学流程有运行基础，不能证明已经完成赛题要求的安全实例。Boyen–Li 组件不属于已确认项目范围，其不存在不再计为待完成项。

## 8 已确认通用构造与隐私边界

### 8.1 固定王老师的通用组合

本项目采用 Wang 等论文 §4.1 的 Construction 1；安全前提以 §4.2 的 Theorem 4.2 为准。匿名两层 HIBE 提供普通隐私，自适应安全 IBS 提供加强认证。发送身份位于第二层，接收身份位于第一层；对接收者身份与消息签名，再加密签名与消息。这个组合顺序已经确定。[S1]

底层方案尚未冻结。接下来从所需安全定义出发，核对具体 HIBE 和 IBS 的算法、定理、模型、采样和参数，然后在可比条件下测量尺寸与速度。软件接口能接入某个后端，不表示该后端已经满足组合定理。

### 8.2 不实施增强隐私的技术含义

Wang 等 §3 的 Definition 9 限制隐私攻击者不能取得目标接收者的解密密钥。其 Definition 10 的加强认证则允许目标接收者已经被腐化，用于覆盖自我伪造。两个游戏的权限不同：不做增强隐私，不会取消对恶意接收者伪造发送者的防护目标。[S1]

Boyen–Li §1 和 §3 的 Definition 5 进一步研究目标接收者持有自己的密钥、但尚未匹配发送者时的消息保护。正常客户端返回失败，不能证明控制密钥与客户端的用户无法读到中间明文。其构造增加匿名 IBE、提取器、可复用提取器及身份熵等条件。该性质不属于本项目实现与验收范围，也不在报告中宣称。[S5]

因此，公开用户名、学号等身份不需要为本项目另行强行赋予 Boyen–Li 所需的秘密熵；身份认证与发钥仍须可靠。API 保持错误发送者和错误接收者返回失败。安全报告明确区分普通隐私、加强认证、接口匹配和密文完整性。

### 8.3 其它 IBME 文献作为相关工作

前期已检索的匿名 IBE 加提取器、增强隐私 CCA、直接环格 IBME 等路线保留为背景文献，不列入本次开发里程碑。2026 年 Yu 等关于重复发送密钥认证的研究仍可用于审查查询一致性；本文只核验过其摘要与构造概述，不能据此宣布既有方案失效或改换通用构造。[S3]

第 18 节保留初次调研的版本记录，其中 [S6]、[S7]、[S8]、[S9]、[S16]、[S17] 的列入不表示计划实现这些协议。论文版本修订和摘要级证据的边界仍须保留。

## 9 底层原语及多类格实例的具体选择

### 9.1 IBS 候选需要扩展旧报告

应同时考虑 Wang 的完整转换版本、Pan Wagner、Foo Li，以及旧报告未充分展开的 Sageloli 等 ACNS 2023 工作。每个候选都应核对自适应性、经典或量子随机预言机、重复密钥与签名查询、分布条件和具体参数，而非只比较向量长度。

| IBS 候选 | 特征 | 必须核验的实现细节 |
|---|---|---|
| Wang 基本 IBS 及自适应转换 | 与当前实现关系直接 | 基本 UF-naCMA 与完整转换的区别 |
| Pan Wagner 2021 [S12] | 紧安全转换及短签名参照 | 转换状态 密钥一致性 哈希模式 |
| Foo Li 2023 [S13] | QROM 中紧安全 一个向量与一比特 | 主密钥秘密种子 用户种子 确定性查询一致性 |
| Sageloli 等 2023 [S14] | SIS 和 RSIS 版本及具体参数 | 非齐次方程 三进制 gadget 与完整采样 |

Foo Li 的算法并非在当前向量后随便加一比特。其秘密种子控制身份密钥和签名采样的重复一致性，实现需要保留相应状态或确定性导出逻辑。论文的签名缩短比较基线是 Pan Wagner，不能把其百分比移用于当前 Wang 教学实现，也不能据 IBS 的 QROM 定理宣称完整 IBME 已获 QROM 证明。[S13]

本轮进一步核对了 Pan Wagner 与 Sageloli 的签名查询游戏：它们在签名查询中重新调用 KeyExt，而自适应转换的发钥会重新采样身份盐。实际系统的一次发钥、多次发送需要另行审查联合分布与证明适配，不能简单加入缓存后沿用全部结论。Foo Li 已明确处理一致性，因此与 ABB10 一起列为下一轮优先精读对象；这不是最终选型，也不是对其它论文安全性的否定。

Sageloli 等提供 SIS、RSIS 实例、具体参数表及参数计算材料。其三进制 gadget 对应模数形式与当前二进制工具不同，不能复用二进制拆分后直接标为论文实现。这条路线可以同时支持矩阵和环格 IBS 比较，是时间充分条件下应纳入的候选。[S14]

具体成本仍须仔细判断：该论文 §8.1 的 Table 7 对基本环格实例 ParamI 给出 20 Mo 签名与 699 Mo 用户密钥，原文估计为 129 bits。它们是论文概念验证参数的理论结果，不是本项目实测；完整自适应实例还需盐、编码和查询损失。首轮因此保留其研究价值，但不因“短签名”名称直接选作竞赛主后端。[S14]

Module-SIS IBS 需要找到或建立真正支持身份发钥和相应安全游戏的完整方案。普通 ML-DSA 或 Falcon 是普通签名体系，不能仅把身份字符串当作公钥，就成为论文要求的 IBS。若需要自行构造，研究量可能接近新论文，应作为独立课题安排。

### 9.2 两层匿名 HIBE 候选

首先核验 ABB10 CRYPTO 2010 的 §4 ROM 构造、Theorem 5 和两层参数，作为论文对应最直接的 HIBE 参考候选。标准模型版本属于另一种实例，应单独审查。Bonsai Trees 等矩阵委派方案用于扩展比较。Latte 有公开实现和结构化格优化价值，但普通 HIBE 的机密性或 CCA 性质并不自动包含所需的匿名性；在匿名性证据明确前，它适合单独研究性能和委派机制，不作为已获准的 IBME 后端。[S4][S15]

Tomita 与 Shikata 的 Module-LWE 匿名 IBE 等文献可提供模格陷门与参数研究参考，但普通匿名 IBE 没有自动获得两层密钥委派能力。只有取得满足相应匿名和自适应安全定义的完整 HIBE 构造后，才可纳入本项目端到端实例。不能把已存在匿名 IBE 写成已存在可替换 HIBE，也不为接入它重新设计另一套通用协议。[S16][S17]

### 9.3 矩阵 环格 模格和 NTRU 的边界

| 类别 | 数学对象 | 项目中的研究重点 |
|---|---|---|
| LWE 与 SIS | 模整数矩阵和整数向量 | 完整参考实例与基础攻击估计 |
| RLWE 与 RSIS | 指定多项式环及理想格 | 环陷门 采样 系数嵌入及环攻击 |
| Module-LWE 与 Module-SIS | 环上的模向量及矩阵 | 环次数与模秩共同选择 完整身份原语 |
| NTRU 型格 | 特定结构与陷门分布 | 委派性能与匿名性条件分别核验 |

在环或模格方案中，总系数维度常涉及环次数 $d$ 与模秩 $r$ 的乘积。它不等于矩阵方案中直接换一个 $n$，也不保证同样数字的维度代表同样安全强度。必须记录环多项式、模数、嵌入、误差分布与攻击模型。

共享“LWE”名称不意味着可以复用同一份参数或证明。ML-KEM 是模块格 KEM，不能直接取代带身份提取或委派能力的 IBE/HIBE。FIPS 203 的参数等级也不能转移到我们自己的 IBME 组合。[S18]

允许在固定通用构造内采用混合组合，例如矩阵 LWE 匿名 HIBE 加 Ring-SIS IBS。应如实说明两种底层假设和各自瓶颈，不能将其标为所有组件都基于环格。Module-LWE 加密组件仍须满足 HIBE 准入条件。

## 10 固定通用构造下的原语选型顺序

先冻结原语准入条件：HIBE 支持两层身份与正确委派，满足王老师定义所需的自适应匿名隐私；IBS 支持自适应身份与消息查询，满足加强认证归约。逐项检查重复取钥、同一密钥多次发送、随机预言机查询和经典或量子攻击者范围。[S1]

再给每套候选做三项验证。第一项是理论兼容性，确认每个原语定理确实满足组合要求。第二项是具体可实现性，列出采样、状态、参数和现成代码情况。第三项才是实测成本，包括委派、签名、胶囊、消息体和内存。

本轮先完成安全目标、首轮原语核验和明确的下一任务。随后落实 ABB10 候选的算法与参数对应，以及 Wang 加自适应转换、Foo Li、Sageloli 等 IBS 的完整成本比较。选定原语后建立矩阵参考实例，研究密文完整性封装，再接入另一套 IBS 或 HIBE 后端，形成同一通用构造下的实例切换。

HIBE 和 IBS 分别选择，不必共用模数、维度或同一论文。优先调查 Ring-SIS IBS 的完整方案，模格身份原语保持具体研究任务；未满足两层匿名 HIBE 条件的加密组件不能进入正式组合。

在时间充分的前提下，不应因开发难度直接排除模格，但也不应同时手写大量未验证后端。每套后端通过数学和安全关口后再进入优化层；这样既能扩展研究范围，也能控制证据质量。

| 恶意接收者 | 持有正确接收密钥并修改客户端 | 能否冒充没有发送密钥的身份进行自我伪造 |
| 重复使用者 | 同一身份同一发送密钥发送多次 | 查询一致性和相关性是否符合定理 |
| 完整性审查对手 | 修改胶囊 头部或消息体 | 能否在保留明文时让非法修改仍被接受 |
| 系统中心 | 掌握主密钥 | 托管信任边界与管理措施是什么 |

隐私游戏和认证游戏可能对挑战身份、发钥、加密与签名查询有不同限制。必须逐条记录，不宜用“满足 IND-CCA 和不可伪造”一句话掩盖差异。应用的用户枚举、网络地址和日志泄漏，也不属于密文匿名定理自动保护的范围。

普通隐私和加强认证按 Wang 定义分别处理。本项目不承诺针对持有目标接收密钥、未匹配发送者的用户实现增强隐私。CCA 只在选定认证封装有相应完整论证后作为独立性质声明，不能自动由基本 CPA 构造继承。

### 11.2 论文算法到代码的对应表

每个后端都需要一份对应表，至少列出：论文版本与哈希、算法和定理编号、代码入口、矩阵尺寸、输入空间、采样分布、哈希预言机、秘密状态、范数限制、证明前提及实现差异。不能只有一条论文引用和若干公式。

特别要检查“重复请求”语义：同一身份再次取密钥时是否复用已有状态；同一消息签名的随机性是否由秘密种子导出；不同进程和重启后是否保持必要的一致性。如果要改变论文的状态模型，应先说明证明为什么仍成立。

### 11.3 建立参数依赖图

参数应沿“方案及定理 → 代数与采样约束 → 正确性误差 → 攻击估计 → 性能”确定，不能从希望的速度倒推不合法参数。至少覆盖以下内容：

1. 维度、模数、gadget 基数和宽度，以及公矩阵接近均匀的条件。当前基本 IBS 的论文维度条件含 $m\ge2n\lceil\log_2 q\rceil$；现有 $m=80$ 小于该值 144，是条件缺口之一，而不是全部问题。
2. 各层陷门谱范数、平滑参数及预像采样宽度，委派后是否继续满足条件。
3. 签名合法范数与验签阈值，归约输出的 SIS 界，以及允许的错误概率。
4. 加密噪声、秘密分布、密钥噪声和消息编码，给出每比特与整条消息的解密失败界。
5. ROM 或 QROM 归约损失、允许查询次数、身份空间与密钥复用条件。
6. 模矩阵、环和模格的结构化攻击及成本模型，并以最弱组件限制整体结论。

高斯符号必须换算一致。若代码概率与 $\exp(-x^2/(2\sigma^2))$ 成比例，而论文采用 $\exp(-\pi x^2/s^2)$，则应使用 $s=\sqrt{2\pi}\sigma$。二者都叫“高斯参数”，仍不能数值直接照抄。

固定选择“128 位”可以作为团队研究目标，但需明确是哪个成本模型下的估计值、哪些组件的归约，以及查询数量和统计误差等前提。不能把估计器输出的一列数字当作 NIST 等级或形式证明。

### 11.4 攻击估计及失败概率记录

使用 lattice-estimator 时应固定提交、依赖、成本模型、攻击列表和完整输入。对 LWE 记录秘密与误差分布、样本数、模数和维度；对 SIS 记录范数类型和归约范数；结构化问题采用适配的估计与额外检查。`estimate.rough` 与完整估计可能采用不同模型，应区分。[S19]

同时保留轻量自查：模线性代数稀疏解、格规约、公开方程和过大范数界、共享随机秘密的相关性、身份查询枚举。估计工具并不能代替这些更简单的攻击检查。

“一万次合法解密全部通过”是功能证据，不能证明失败概率小于 $2^{-128}$。例如在独立同分布且零失败的试验假设下，95% 置信上界量级约为 $3/N$；密码学所需的极小失败率仍依赖数学界与采样条件。

## 12 软件架构与优化实现

### 12.1 通用构造层与原语层分别配置

建议新增完整的方案注册体系，固定协议标识为 Wang 的 HIBE 加 IBS 组合，让配置选择 HIBE 后端、IBS 后端、认证封装版本、参数集及安全能力。普通 IBE 缺少委派能力，不能伪造一个没有意义的 `derive` 来硬凑兼容。不开发提取器或增强隐私协议插件。

每个已注册方案附能力清单和版本标识。配置加载时检查所需能力，不兼容的匿名性、查询模型、环参数或状态语义直接报配置错误。教学、研究候选、已核验参考实现应有明确状态，不能仅凭参数名称叫作 `production`。

HIBE 与 IBS 应分别配置参数，允许模数和维度不同。当前协议能够分别接受两套参数，这一点应继续保留。统一配置指统一管理和验证，不是强迫所有组件使用一个 $n$ 和一个 $q$。

### 12.2 认证胶囊与大消息封装

现在逐比特加密整个签名和消息，既产生巨大密文，也限制用户消息长度。应研究符合所选通用构造和安全目标的胶囊加消息体结构，使用格原语处理短密钥材料，以经论证的对称认证加密处理大消息。

设计时必须明确：发送者身份、接收者身份、方案版本、密钥版本、格胶囊和消息体分别由哪一条签名或认证关系绑定；认证标签覆盖哪些规范字节；修改胶囊但保持解出的短密钥不变时能否被拒绝；消息体长度和随机 nonce 的策略是什么。若引入新组合，先给出安全论证与完整性定义，再做优化实现。

不要在依赖关系中形成“签名包含密文，而密文又包含同一签名”的循环。先写清消息编码和计算顺序，核验安全定理能否复用。公开附加签名也可能破坏身份隐私，必须一起评估。

### 12.3 数学参考与原生性能层

先实现可审查的 Python 或 Sage 参考版本，再建立 C/C++ 运算层，以同一公开测试向量进行差分核对。优先优化实测耗时占比高的矩阵乘法、哈希展开、采样、委派、序列化及环乘法。

若使用 Sage，按仓库规则在 WSL 的 `~/miniconda3/envs/sage` 环境运行。文档和脚本使用这个可移植路径，不写死另一台机器的用户名。Python、Sage 与原生层应固定整数中心化和序列化规则。

NTT 并不适用于随意的环和模数。必须检查根的存在、表示和变换长度；三进制 gadget 方案的模数也不能直接套用常见二进制环库。使用第三方实现时记录代码版本、许可、参数和所修改部分。

可缓存身份公矩阵、哈希展开等确定性公开数据，并单独评测冷启动和缓存命中。秘密密钥缓存需要生命周期控制；加密随机秘密和噪声不得为了省运算跨消息复用。当前逐比特独立秘密是早期共享掩码泄漏问题修复的一部分，不能回退该修复来追求速度。

### 12.4 运行可靠性与密钥管理

软件应检查尺寸、模系数规范范围、整数溢出、重复字段、长度上限和资源上限。错误输入不能触发无限内存分配或严重异常。密钥与密文格式应可识别版本，跨后端、跨参数或跨主公钥的混用应被拒绝。

展示软件中使用的主私钥应属于演示环境，不进入版本库或公开材料。发钥应校验身份归属，明确接收密钥和发送密钥的权限。撤销与密钥轮换可以用 epoch 等机制研究，但若改变身份语义，要写入协议与证明映射，不能仅在 UI 隐藏旧密钥。

## 13 测试与对抗验证计划

### 13.1 从现有测试扩展到赛题证据

| 层级 | 必测内容 | 所支撑的结论 |
|---|---|---|
| 代数 | 矩阵维度 模运算 陷门关系 签名方程 | 实现满足数学关系 |
| 采样 | 标量及目标余类分布 截断误差 统计比较 | 发现实现偏差并辅助条件核验 |
| 序列化 | 往返 规范编码 截断 追加 重复字段 超长输入 | 格式明确并能拒绝非法输入 |
| 协议 | 双方正确 三种错误匹配 多用户多消息 | 功能语义及批量运行正确 |
| 密钥一致性 | 重复取钥 重复签名 多进程 重启 | 实现符合论文状态和查询模型 |
| 对抗 | 公共参数伪造 自我伪造 胶囊篡改 身份枚举 | 检查具体攻击与回归 |
| 优化差分 | 参考层与原生层的中间量及最终结果 | 优化实现保留算法行为 |

随机错误签名测试只是其中一类。必须保留当前线性代数攻击作为修复核验：目标是让公开构造的攻击密文被拒绝，同时保证合法签名和解密全部成功。既有攻击脚本成功返回退出码 0，只表示攻击演示运行成功，不能在持续集成中误写为“安全测试通过”。

对密文头、版本、参数标识、格胶囊各系数、签名、消息体和认证标签分别做定向篡改。当前一字节可接受反例应成为新组合的明确回归用例。还需测试换接收者、换发送者、跨系统公钥、重放和旧密钥版本；重放是否拒绝由应用策略决定，应单独记录。

建议为最终批量正确性设定覆盖身份长度、中文和 UTF-8 编码、空消息、边界长度、多个发送者与接收者的试验集。例如可设一万组作为内部阶段目标，但这不是官方固定次数，也不允许丢弃失败样本再报“全部通过”。

针对恶意接收者的本轮安全测试聚焦自我伪造：即使掌握自己的接收密钥，也不能冒充没有发送密钥的 Alice。正常 API 的错误发送者拒绝仍需测试；该功能不写成增强隐私证明，不设置 Boyen–Li 身份熵或中间值保密的验收项。

### 13.2 可复现记录格式

每次记录源代码提交、参数及方案版本、原语论文版本、实验种子或生产随机模式、身份和消息长度、重复次数、环境、成功与失败数、原始数据、统计脚本及安全声明。生产密钥和生产随机秘密不能为了复现公开。

建议提供已知答案测试向量和跨语言测试向量。秘密相关向量只使用专用测试种子，并标明不可用于实际通信。论文安全参数测试和教学参数测试分开运行和出图。

## 14 性能评测与创新证据

### 14.1 比较维度与统计口径

完整评测应同时有“不同方案”和“不同参数”两条轴，再按消息长度、身份长度、线程数和优化开关展开。可选消息长度包括 0、32、256、1024 字节及更大消息；不支持某个长度的方案如实记录上限或采用一致且经过论证的消息封装。

测量对象应区分系统公钥、主密钥、发送者密钥、接收者密钥、委派密钥、裸签名、格胶囊、消息体、完整密文和序列化开销。时间应区分系统建立、两类发钥、委派、签名、验签、加密、解密和完整用户操作。

运行报告至少有中位数、四分位距及必要时的 p95，注明预热、重复次数、线程和缓存条件。内存测进程峰值 RSS，并解释原生分配与 Python 对象内存；只报 `tracemalloc` 不能覆盖 C/C++ 后端的全部内存。

同等安全目标下比较需要同时控制攻击模型、证明损失、消息和身份长度、失败概率与能力。较弱隐私、不同认证模型或没有匿名性的方案可以作为单独参照，不能直接排在“最安全且最快”同一序列中。

### 14.2 建议形成的图表

建议给出安全能力矩阵、参数及估计摘要、密文组成图、时间分解图、长度与加密时间曲线、签名压缩收益、缓存与线程消融，以及尺寸时间内存的综合比较。所有图表可追溯到原始 JSON 或 CSV。

特别值得研究“短签名是否仍是主瓶颈”。当前逐比特封装会极大放大签名尺寸；经论证采用胶囊消息体包装后，胶囊或采样时间可能成为主成本。优化对象会随后端和包装改变，应由新基准决定。

### 14.3 可形成项目贡献的研究问题

可以选择以下问题作为主要贡献，但需要结果出来后才能宣称收益或创新：在相同认证模型下，完整 IBS 候选的签名与采样成本差异；在相同通用构造下，矩阵与环格组件的尺寸及委派成本差异；LWE 匿名 HIBE 与 Ring-SIS IBS 混合组合的实际瓶颈；认证封装对篡改拒绝和大消息效率的影响；缓存、序列化和原生运算的安全保持优化。

建议选择一项主要研究问题，加一项工程优化形成清晰主线。多写几种算法并不自动形成创新；复现已有论文应标注为复现，新的组合或参数选择需要解释证明依据，原创安全构造则必须经过更严格审查。

## 15 按成果验收推进的工作包

本计划没有按日期压缩范围。每个工作包完成后，以可审查的文件、代码和实验过关，再推进依赖任务。理论、原语、工程和评测可以按明确接口分工，具体人员由团队自行安排。

### 15.1 G0 明确目标与材料版本

输出已确认的 Wang 通用构造、普通隐私和加强认证目标、赛题对应表、文献和代码版本目录，以及用户身份、系统中心和密钥复用的应用语义。明确不实施增强隐私。归档首轮 HIBE 和 IBS 文献的版本、哈希及证据位置。

验收条件是每项核心性质都有可定位的定义和候选定理；未核验前提明确列出，官方要求与内部目标分开。架构、接口规范、协作提示和报告必须一致，不能继续把增强隐私列为待开发里程碑。

### 15.2 G1 精确选型与证明映射

输出 HIBE 和 IBS 的原语准入矩阵、算法定理对应表、状态与查询一致性审查，以及参考后端和优化候选决定。优先核验 ABB10 的具体 HIBE 构造，以及 Wang 完整转换版本、Pan Wagner、Foo Li 和 Sageloli 的 IBS。首轮之后再扩展其它 HIBE 候选。

验收条件是所有组合前提都有满足它们的具体候选；不能用“可能匿名”或“应该满足 UF-CMA”放行。若需要新的转换或完整性组合，应写出独立论证。

### 15.3 G2 陷门 采样与参数体系

输出数学参考实现、采样分布说明、参数约束检查器、攻击估计输入和固定版本结果、正确性与失败界说明。根据候选实现二进制或三进制 gadget、矩阵或环上的陷门，而不是修改符号后共用错误算法。

验收条件是所有参数满足选用定理和采样要求，公开稀疏解等基础攻击检查完成，合法运行具有明确正确性依据。尚未达到目标安全成本的参数保持教学或研究标识。

### 15.4 G3 完整 LWE SIS 参考实例

输出论文算法一致的原语、完整认证组合、序列化、公共测试向量、四种身份匹配和自我伪造篡改测试。可以保留当前教学后端，但作为单独参照。

验收条件是实际完整实例满足选定安全模型，当前公开参数伪造和一字节篡改反例在新目标组合中得到处理，合法批量测试全部通过。接口测试通过与安全证明映射均需提供。

### 15.5 G4 结构化格和第二套实例

输出已有 Ring-SIS IBS 的完整算法、参数与实现研究，在同一通用构造中形成至少另一套可切换组合。环格和模格 HIBE 只有在两层匿名、自适应安全和采样条件都明确后才进入实现。纯 Module-SIS IBS 若没有成熟可核验候选，应另列研究课题，不冒充完成。

验收条件是第二套实例实际端到端运行，能力清单与第一套可比，所有参数、环和模结构明确。若最终选择混合方案，说明其各组件假设，不把混合实例标成纯模格。

### 15.6 G5 优化与公平评测

输出原生运算层、尺寸和速度优化、参考差分测试、统一性能入口及原始数据。针对签名、胶囊、委派、采样与序列化分别进行消融。

验收条件是优化没有改变未论证的分布或复用秘密随机数，收益在同样参数与能力下复现，时间与内存均有记录。没有改善的指标和优化代价同样披露。

### 15.7 G6 应用演示与最终交付

输出演示软件、技术报告、测试报告、参数与安全报告、第三方来源说明、复现指南及答辩材料。建议演示匿名公告板或双方身份匹配的消息交换场景，展示合法匹配、三类错配、公开伪造和密文篡改拒绝、实例切换和性能结果。

验收条件是从干净环境可按文档完成演示，默认配置具有明确状态，演示数据与主私钥可安全重建，所有展示数字都能追溯到提交和实验记录。答辩能解释采样、身份绑定、密钥复用、参数与攻击，而非只能操作界面。

## 16 接下来应优先研究的技术问题

第一，Wang 的 Definition 10 如何覆盖自我伪造，其“新消息”条件与赛题要求的密文字节篡改拒绝有什么差异？固定基本组合后，需要明确额外认证封装的目标与证明，不降低已有篡改验收。

第二，ABB10 两层 HIBE 的实际矩阵、委派、采样和参数如何对应代码？需要分清原论文算法与现有拼接式教学后端，并量化委派宽度及归约损失。

第三，Foo Li、Sageloli 等和 Wang 完整转换版本在同一密钥复用模型下，哪些能够直接满足所选通用构造？要取得完整参数并实现必要秘密种子、状态和采样，不能只对裸方程测速。

第四，如何得到兼顾失败界与攻击成本的真实参数？需要谱范数界、Gaussian 参数换算、各阶段噪声和归约损失，随后才使用固定版本估计器。

第五，哪些结构化格组件能在固定通用构造下形成完整实例？先核验已有 Ring-SIS IBS；Module-SIS 身份签名和两层匿名 HIBE 需要完整算法与定理，不能用普通 KEM、匿名 IBE 或普通签名替代。

第六，大消息封装如何同时保护胶囊与消息体并保持身份隐私？这个问题应先写计算顺序、安全论证和篡改实验，再进入优化层。它可能比单纯减少若干签名系数更影响最终系统。

这些问题都可以继续推进，无需先确认截止日期。AI 可以帮助搜集材料、推导、编写代码和交叉核验，但模型生成的证明与参数仍需回到论文、数学约束和实验验证；重复生成同一结论不等于独立证据。

### 17.1 一字节篡改实验的复现片段

下面使用专用固定种子，不能用于生产。它对当前代码基点运行一个合法密文和一个篡改密文的解密，不保存或输出私钥。示例依赖当前模数系数编码的 3 字节宽度，其他方案不能照搬这个定位方式。

```python
from ibme.core.randomness import DeterministicRandom
from ibme.hibe import ABB10HIBE
from ibme.ibs import SisIBSBackend
from ibme.protocol import (
    BaselineIBME, BASELINE_DEBUG_PARAMS,
    BASELINE_DEBUG_IBS_PARAMS, is_bottom,
)

def rng(tag):
    return DeterministicRandom(b"review-2026-10-03:" + tag)

p = BaselineIBME(ABB10HIBE(), SisIBSBackend(rng=rng(b"ibs")))
pk, msk = p.setup(BASELINE_DEBUG_PARAMS,
    ibs_params=BASELINE_DEBUG_IBS_PARAMS, rng=rng(b"setup"))
ek = p.skgen(msk, b"Alice")
dk = p.rkgen(msk, b"Bob", rng=rng(b"rk"))
raw = p.encrypt(pk, ek, b"Bob", b"A", rng=rng(b"enc")).to_bytes()
x = int.from_bytes(raw[-3:], "big")
bad = raw[:-3] + ((x + 1) % BASELINE_DEBUG_PARAMS.q).to_bytes(3, "big")
before = p.decrypt(pk, dk, b"Alice", raw, rng=rng(b"dec"))
after = p.decrypt(pk, dk, b"Alice", bad, rng=rng(b"dec"))
print(len(raw), x, before == b"A", after == b"A", is_bottom(after))
# 4109477 7276 True True False
```
