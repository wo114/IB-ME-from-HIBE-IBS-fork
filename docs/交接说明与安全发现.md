### 1.2 逐条说明

#### ① Sage 环境路径改为机器中立（5 处）

**改动：** `/home/youzi/miniconda3/envs/sage` → `~/miniconda3/envs/sage`

涉及 `AGENTS.md`、`README.md`、`ARCHITECTURE.md`、`notes/ib-me-hibe-ibs-design.md`、`docs/M3_CODE_REVIEW.md`。

**原因：** 原路径里的 `youzi` 应该是你的 WSL 用户名。这台机器的 WSL 用户是 `zhang`，该路径不存在。仓库以文件夹形式在队员间传递，写死任一台机器的绝对路径，换一台就是错的。`~` 写法在两台机器上同时成立。

`AGENTS.md` 另加了一条规矩：今后不得把绝对路径写死。

**验证：** 本机已在 `~/miniconda3/envs/sage` 安装 SageMath 10.9，实跑 `GF(257)` 上 8×80 矩阵求秩与 LLL 约化均正常。

#### ② 新增 `.gitattributes`，固定换行策略

**改动：** 新增文件，内容为 `* text=auto eol=lf` 加二进制类型标注。

**原因（实测）：** 改动前工作树是混合换行态——

```
29 个文件  索引 LF / 工作树 CRLF
22 个文件  索引 LF / 工作树 LF
 2 个文件  索引 LF / 工作树 mixed
 7 个文件  二进制
```

而两台机器的 `core.autocrlf` 都没有显式配置，走的是 Git for Windows 内置默认。只要有人在 WSL/Linux 侧对同一份工作树跑 git，就会出现整文件级的假 diff。把策略写进仓库后，不再依赖任何人的本地配置。

选 LF 而非平台原生 CRLF，是因为项目同时在 Windows、Git Bash 和 WSL 下运行，将来加 `.sh` 脚本时 CRLF 会直接让 bash 报错。

**验证：** 工作树 30 个文件按新属性重新检出；索引内容总校验和前后一致（`7a35153545f4150c`），`git diff` 对全部文件为空——**只改换行，未动任何内容**。改动后换行状态为 54 LF + 7 二进制。

> 你 `git pull` 后可能看到部分文件被规范化，这是预期行为，内容没有变化。

#### ③ `.gitignore` 补充演示产物规则

**改动：** 新增 10 类忽略规则，覆盖 `*-state/`、`*.ibme-ct`、`demo-*.bin`、`real-*.bin`、`message.bin`、`ciphertext.bin`、`tampered*.bin`、`recovered*.bin`、`.pytest-tmp-*/`、`*.bundle`。

**原因（实测）：** `docs/COMPETITION_DEMO_AND_DEFENSE.md` 与 `IMPLEMENTATION_SPEC.md` §7 的演示命令都在仓库根目录产出文件。逐个执行 `git check-ignore` 确认，改动前这 10 类**全部未被忽略**，后果有两条：

**验证：** 在仓库根目录完整跑了一遍 mock 演示流程（生成 `demo-state/msk.bin` 等产物），`git status` 全程只显示 `.gitignore` 一行。同时确认无任何已跟踪文件被新规则误伤。

#### ④ `AGENTS.md` 新增 §2.1「队员之间交换仓库」

## 2. 实测发现的问题

### 2.1 【严重】SIS-IBS 可被平凡伪造，IB-ME 强可认证性不成立

#### 现象

在 `ibs-education` 参数下，**不持有任何签名密钥**即可伪造通过验签的签名。两级验证：

**原语级**（`experiments/attacks/forge_ibs.py`）：

```
身份 b'Alice'（从未调用 key_extract）
||z||_2 = 185.81   验签界 beta = 789.04
verify() -> True
```

**协议级端到端**：攻击者仅用公钥 `mpk`，伪造出接收者能正常解密、并归因于被冒充发送者的密文：

```
接收者解密出: AUTHORIZED BY ALICE: release the funds
并会认为该消息来自 Alice
```

这正是指导论文定义 3.2.10 的强可认证性游戏——也是第三章的**核心定义贡献**。

#### 根因

`params/ibs-education.yaml` 为 `s'=64` 给出的论证是：

> 该界仍拒绝中心化代表元的均匀向量（‖·‖ 可达 128·sqrt(152) ≈ 1578 > 789）

这检查的是**稠密**向量（152 个分量全非零）。但攻击者不需要稠密解：`F_id` 是 `8 × 152`，任取 8 个线性无关的列解方程、其余 144 个分量置零即可。**论证检查了错误的对手模型。**

更本质的原因是 **`beta = 789 > q = 257`**。当范数界超过模数时，`F_id · z = h2 (mod q)` 退化为普通线性方程组求解。

#### 无法通过收紧验签界修复（实测）

方案要成立的必要条件是存在 `beta` 满足 `max(诚实签名) <= beta < min(可达伪造)`。实测数据：

| 来源 | 样本量 | min | median | max |
|---|---|---|---|---|
| 诚实签名 | 1000 | **184.7** | 517.2 | **784.7** |
| 线性代数伪造 | 30（每组 60 次列子集搜索取最短） | 100.5 | 129.0 | 150.6 |
| **LLL + Babai 伪造** | 1 | — | — | **6.71** |

LLL 结果的细节：

```
朴素解              ||z|| = 451.76
解格 152 x 152, 最短基向量 ||b1|| = 6.32
LLL + Babai 约化后  ||z|| = 6.71   非零分量 33/152
送入真实 backend.verify(...) -> True
```

**诚实签名最短 184.7，LLL 伪造 6.71，相差约 28 倍。** 任何能接受诚实签名的界都必然接受该伪造，因此收紧 `s'` 无法修复。

#### 独立工具确认

用 `lattice-estimator`（格密码标准估计工具）跑同一实例：

```
SISParameters(n=8, q=257, length_bound=789.04, m=152)
  → 拒绝估计："SIS trivially easy. Please set norm bound < q."
```

工具本身判定该实例平凡可解，与实测攻击一致。

#### 边界说明

**这不是论文构造 3.4.1 的缺陷。** 论文的参数选取要求 `q = beta · poly(n)`，即模数必须相对范数界足够大；项目参数恰好反了。这是**实例化参数选择**的问题，不是构造问题。报告中必须这样表述。

### 2.2 【严重】HIBE 的 LWE 实例约 2^33

同一工具跑 HIBE 侧参数：

```
LWEParameters(n=8, q=524288, Xs=均匀 mod q, Xe=D(σ=1.0), m=473)
  usvp         rop ≈ 2^33.1
  bdd          rop ≈ 2^33.1
  dual_hybrid  rop ≈ 2^33.4
  dual         rop ≈ 2^38.8
```

约 **33 bit**——2^33 次运算，笔记本几分钟量级。密文隐私在教学参数下同样不成立。

参数来源：`ABB10_DEBUG_PARAMS`（n=8, q=2^19, s=1.0），样本数 `m = len(c2) + 1 = 472 + 1 = 473`（v2 起每个明文比特一条独立 LWE 样本，每个样本用新鲜秘密）。

工具自身校准：同一环境跑 Kyber512 得 `primal_usvp = 2^143.8`，与公开基准吻合。

### 2.3 【中】测试套件对代数伪造存在盲区

全量测试 **333 passed, 10 skipped**（Python 3.14.7，本机实测 520.73s），与报告记录一致；但方案同时可被伪造。

原因在 `tests/test_ibs_contract.py:196 test_random_forgery_verify_false`：

```python
z = [(b % 13) - 6 for b in rng.read(pk.f_id_cols)]
...
assert backend.verify(pk, b"Alice", b"payload", forged) is False
```

用的是**随机**向量，必然不满足 `F_id · z = h2`；代数伪造满足方程，直接穿过。

建议把 `experiments/attacks/forge_ibs.py` 的攻击固化为回归测试——与当初处理共享掩码泄漏的做法一致。

### 2.4 【低】文档承诺与实现不符

`ARCHITECTURE.md` §3 推荐目录中列出、但实际不存在的文件（逐个 `test -e` 验证）：

```
✗ tests/test_security_properties.py
✗ params/competition.yaml
✗ experiments/parameter_sweep.py
✗ experiments/test_vectors/
✗ src/ibme/protocol/enhanced.py
```

`IMPLEMENTATION_SPEC.md` §5 规定的 AEAD 混合加密：`grep -rl "AEAD\|aead" src/` 命中 **0 个文件**，导致只能加密 400 B 以内的短消息。

评委若对照架构文档读代码会发现这个落差。要么补齐，要么把文档改成与实现一致。
